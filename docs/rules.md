# Rule reference

This linter operationalizes ideas from [ASD-STE100](https://www.asd-ste100.org/) (Simplified
Technical English) -- one word, one meaning; short, unambiguous sentences; no hidden
optionality -- as six automatable tests, plus a set of structural checks, a CSV-registry
integrity family, and word/sentence/paragraph budgets. This document is the catalog: what each
test detects, why it matters, its rule-ID scheme, how severity is resolved, and real verified
examples for every one of them.

Every example below was produced by actually running `ste_lint.py` against a real fixture file
with `the default preset` (or `the veistra preset` for the CSV-integrity family, see that
section) -- nothing here is invented. Run the commands yourself to reproduce.

## The rule-ID scheme

Rule IDs look like `STE-<test>-<CATEGORY>-<seq4>`, e.g. `STE-T1-SUB-0104` or
`STE-S7-BARENUM-0001`.

**The `STE-` prefix is a leftover from this tool's origin as an internal linter at a company
called Veistra.** It is not a generic OSS-friendly name, and renaming it is a decision the
maintainer of this project still has to make -- not one this preset makes for you. Renaming it
is not just a config edit: the prefix is baked as a literal string into every rule ID recorded
in `src/ste100/data/*.json` (generated by `devtools/builddata/*.py`), so a rename means regenerating those
files, not just changing a string somewhere. See `the default preset`'s
`rule_id_taxonomy.note_for_maintainer` for the same note in-repo.

T1/T2/T3(hedge words)/T6 rule IDs are pre-assigned per-entry in `src/ste100/data/*.json` at data-build
time. T4/T5/structural(`S7`)/`csv`/budget rule IDs are small, closed enumerations assigned as
constants in `src/ste100/rule_ids.py` -- see `EXPLAIN_TEXT` there for the authoritative one-line
description of every fixed ID.

## `--explain RULE_ID`

Resolves any rule ID to its explanation -- the fixed one-liner from `src/ste100/rule_ids.py` for
T4/T5/structural/csv/budget IDs, or the full data entry (pattern, suggestion, source) for
T1/T2/T3/T6 IDs, which are looked up in `src/ste100/data/*.json`.

```
$ ste100 --config the default preset --explain STE-T5-EARS-0001
STE-T5-EARS-0001: T5 Non-atomic: sentence does not conform to an EARS template (spec §8.5, O2).

$ ste100 --config the default preset --explain STE-T1-SUB-0104
STE-T1-SUB-0104: {
  "pattern": "utilize",
  "suggestion": "use",
  "alts": [
    "use"
  ],
  "source": "vale_redhat.simple_words",
  "id": "STE-T1-SUB-0104"
}
```

## Severity: tiers, profiles, and precedence

There are three severity tiers: **error** (fails the run -- nonzero exit code), **warning**
(shown, does not fail the run), and **review** (only shown with `--stats`; advisory).

Severity for a finding is resolved once per check, by `Engine.severity()` in `src/ste100/engine.py`.
Read the precedence in this exact order -- it is subtle and you will hit it:

1. **The `prose` profile-wide cap, applied first, unconditionally.** If the target file's
   profile is `prose` and the check is not T1, T3, or T6, the finding is forced to `review`,
   *before* any rule-specific override is even consulted. This means: in the `prose` profile,
   T1/T3/T6 stay at whatever tier they'd otherwise get (normally `error`); everything else --
   T2, T4, T5, structural checks -- is always `review`, no matter what `severity_overrides`
   says for that rule. See the verified example below.
2. **A rule-specific override for the exact profile**, from `severity_overrides` in the config.
   The first entry in the list whose `rule` matches and whose `profile` equals (or lists) the
   current profile wins outright, regardless of where it sits in the list relative to a
   wildcard entry.
3. **A rule-specific override with `profile: "*"`** (applies to every profile) -- but a later
   specific-profile match for the same rule still wins if one exists anywhere in the list; a
   wildcard match only sets the tentative answer and keeps scanning.
4. **`severity_defaults` in the config**, keyed by rule name.
5. **The hardcoded default** passed as a literal at the call site in `src/ste100/checks_*.py`
   (e.g. `self.severity("T1", unit.profile, "error", test="T1")`), used when the rule has no
   `severity_defaults` entry.

### Verified example of the prose-profile cap

`must_keyword` has a rule-specific override of `warning` for every profile except `spec`
(`error`). But under `prose`, the cap applies first and wins:

```
$ ste100 --config the default preset --profile prose --stats tests/corpus_dirty/dirty_structural.md
...
dirty_structural.md:6:1 REVIEW structural STE-S7-MUST-0001 -- Structural: 'must' used; 'shall' is the mandatory keyword (O3).
```

Not `warning` (the rule-specific default for non-spec profiles) -- `review`, because the cap
fires first and the check's test is `structural`, which is outside `{T1, T3, T6}`.

### Retuning a rule's default tier

`severity_defaults` maps a rule name to the tier it reports at when nothing more specific
applies. It sits below `severity_overrides` (which can target a single profile) and above the
call-site literal in `src/ste100/checks_*.py`, so a rule absent from the block still falls back
to its built-in default.

A caveat worth knowing: a `severity_overrides` entry with `profile: "*"` always beats
`severity_defaults`, so retuning a rule that already has a wildcard override has no visible
effect. Change the override instead. And the `prose` profile's review-cap is applied *before*
any of this, so within `prose` only T1/T3/T6 can reach error tier no matter what you set.

Both shipped presets keep the block's values in sync with the call-site literals, so editing
one entry changes exactly that rule rather than shifting a pile of unrelated tiers.
## T1 -- Replaceable

**What it detects:** a word or short phrase with a simpler, unambiguous, ASD-STE100-style
replacement -- "utilize" instead of "use," "perform an evaluation" instead of "evaluate," filler
openers like "It is" that can just be deleted.

**Why it matters:** every synonym for a concept is a second thing a reader (or a translator, or
another writer copying your phrasing) has to learn maps to the same meaning. STE's core
discipline is one word, one meaning; T1 is the mechanical enforcement of that discipline against
a curated substitution table.

**Data:** `src/ste100/data/substitutions.json` (`rules`: pattern -> `{id, suggestion, alts, source}`).
Sources cited in the data: `vale_redhat.simple_words`, `vale_microsoft.wordiness`,
`retext_simplify`, and a merged `wordy_and_complex` list whose components were not
recorded. The first three are third-party; see the "Data provenance" section below.

**Severity:** `error` in every profile (T1 is one of the three tests the `prose` fallback keeps
at `error`; see the precedence section above).

**Verified before/after:**

```
Before: "We utilize the cache to speed up requests."
$ ste_lint.py --config the default preset --profile prose t1_before.md
t1_before.md:3:4 ERROR T1 STE-T1-SUB-0104 -- Replaceable: 'utilize' -> 'use'.
    We utilize the cache to s...

After:  "We use the cache to speed up requests."
-> 0 findings
```

`--fix` applies unambiguous T1 substitutions automatically (see `src/ste100/fixer.py`); it does not
touch any other test.

## T2 -- Unfalsifiable

**What it detects:** a quality claim with no number, unit, or named acceptance condition
attached -- "fast," "responsive," "several bugs" -- nothing a reader could check pass/fail
against.

**Why it matters:** an unfalsifiable claim can't be verified, so it can't be a requirement and
it can't be tested. This is INCOSE R7 and QuARS' core complaint about weak requirements
language, and NASA's SEH makes the same point about design docs: if you can't measure it, you
haven't actually said anything.

**Suppression:** T2 does not fire on a sentence that already has a number with a unit (e.g.
"200ms"), or that references an ID with one of a configured set of prefixes (`t2_id_prefixes` in
`src/ste100/data/vague.json`'s `suppression` block: `TRU-`, `DEC-`, `TL-`, `TEST-`, `REQ-`). **Those
prefixes are Veistra's own document-control ID scheme** and won't match a generic project's
requirement/ticket IDs (e.g. `JIRA-123`, `#456`) -- the numeric+unit suppression still works for
everyone, but the ID-reference suppression is currently dead weight outside the original
project. This lives in `src/ste100/data/vague.json`, out of scope for this preset to change; flagged
in `docs/configuration.md`.

**Data:** `src/ste100/data/vague.json` (`terms`: pattern -> `{id, source}`).

**Severity:** `warning` by default; capped to `review` under `prose`.

**Verified before/after:**

```
Before: "The dashboard is fast."
$ ste_lint.py --config the default preset --profile reference --stats t2_before.md
t2_before.md:3:18 WARNING T2 STE-T2-VAG-0034 -- Unfalsifiable: 'fast' with no number, unit, or named acceptance condition.
    ...e dashboard is fast.

After:  "The dashboard loads in 200ms."
-> 0 findings
```

## T3 -- Optional

**What it detects:** language that quietly makes a requirement optional or escapable, in five
flavors: escape clauses ("as appropriate," INCOSE R8), open-ended clauses ("etc.," INCOSE R9),
superfluous infinitives ("needs to be able to," INCOSE R10), optionality (a single non-`shall`
modal verb, or a multiword optionality phrase like "if possible"), and hedge words ("apparently,"
"possible," "will" as a softener -- source: `retext_intensify.hedges`, with a handful of
ambiguous verbs gated on following context, e.g. `expect` only counts as a hedge before "as" or
"to").

**Why it matters:** STE and NASA's ARM/QuARS tooling both flag this because optionality hidden
in prose (rather than stated as an explicit exception) means two readers can disagree in good
faith about whether a requirement was actually met.

**Data:** `src/ste100/data/hedges.json` (`escape_clauses`, `open_ended_clauses`, `optionality`,
`superfluous_infinitives`, `hedge_words`, plus `ambiguous_hedge_verbs_need_context`).

**Severity:** `error` for escape/open-ended/superfluous/hedge and for multiword optionality
phrases; `warning` for a single modal verb outside `spec` (`error` inside `spec`, since a
formal requirement should use exactly one mandatory `shall`). T3 is one of the three tests kept
at `error` under the `prose` cap.

**Verified before/after (five T3 sub-rules in one fixture, run against `spec`):**

```
$ ste_lint.py --config the default preset --profile spec tests/corpus_dirty/dirty_t3.md
dirty_t3.md:4:13 ERROR T3 STE-T3-ESC-0002 -- Optional (escape clause): 'as appropriate'.
dirty_t3.md:4:79 ERROR T3 STE-T3-OPEN-0005 -- Optional (open-ended clause): 'etc.'.
dirty_t3.md:6:16 ERROR T3 STE-T3-MOD-0007 -- Optional (optionality): 'if possible'.
dirty_t3.md:6:69 ERROR T3 STE-T3-SUP-0004 -- Optional (superfluous infinitive): 'to be able to'.
dirty_t3.md:8:1  ERROR T3 STE-T3-HDG-0014 -- Optional (hedge): 'Apparently'.
```

Rewritten to remove the hedges ("Fix the bug according to the design doc," "Support mice and
keyboards," "Ship the patch," "The tool exports data," "The build passed") clears all five.

## T4 -- Referentially open

**What it detects:** two shapes. (1) A pronoun (it, this, that, they, previous, following, ...)
with no antecedent identifiable in the same unit. (2) A comparative or superlative ("faster,"
"greatest," "more reliable") with no stated baseline.

**Why it matters:** Femmer et al.'s empirical work on requirements smells found both patterns
correlate strongly with real ambiguity in practice -- a pronoun that reads clearly to the author
often has two plausible antecedents to a fresh reader, and "faster" without "than what" is not
a testable claim.

**Data:** pronoun and irregular-comparative word lists live in `presets/*.json`
(`t4_pronouns`, `t4_comparative_irregulars`, `t4_comparative_exclusions`,
`t4_comparative_min_stem_length`); IDs are assigned by `src/ste100/rule_ids.py:_seq_ids()`.

**A verified quirk worth knowing:** a stated baseline (`"... than X"` immediately following the
comparative) suppresses the finding for `t4_comparative_irregulars` words and for the generic
`-est` / `more X` / `most X` shapes -- but **not** for the generic `-er than` shape, because the
regex that matches that shape already consumes the word "than" as part of the match itself, so
the suppression check is skipped whenever "than" is already inside the match text. Confirmed by
running the linter:

```
"The new cache is faster than the old LRU cache." (spelled-out baseline!)
$ ste_lint.py --config the default preset --profile reference --stats t4_after.md
t4_after.md:3:18 WARNING T4 STE-T4-COMP-9999 -- Referentially open: comparative 'faster than' with no stated baseline.
```

This still fires *despite* a stated baseline, for any word matching the generic `-er than`
shape. The clean rewrite avoids the comparative construction entirely rather than trying to
satisfy the check with a `than`-clause:

```
"The new cache responds in 10ms. Cache v1 took 40ms."
-> 0 findings
```

**Severity:** `warning`, capped to `review` under `prose`.

## T5 -- Non-atomic

**What it detects:** a sentence that packs more than one requirement, or is structurally too
tangled to atomically verify: more than one `shall` in a sentence; a `spec`-profile sentence
with zero `shall` (not a requirement at all -- `review` tier, since it may be legitimate
narration); a second-or-later combinator (and/or/then/unless/...) in one `spec` sentence;
`and/or` (always -- MIL-STD-961E and NASA's SEH both call it out as never acceptable in a
requirement); an oblique `/` outside a unit or fraction; more than 3 of `,;:` in one sentence
(NASA guidance on requirement complexity); and, in `spec`/`design`-named profiles specifically,
non-conformance to an EARS template (see the note below -- this is profile-*name*-gated, not
profile.tests-gated).

**Why it matters:** one sentence, one testable statement. A sentence with two `shall`s can pass
half and fail half with no way to say the sentence itself passed or failed.

**Data/logic:** almost entirely in `src/ste100/checks_atomicity.py` (the `EARS_RE` regex approximates
the five EARS templates -- Ubiquitous / State-driven / Event-driven / Optional-feature /
Unwanted -- per spec §8.5). Combinator word list and punctuation threshold are config-driven
(`t5_combinators`, `t5_punctuation_density_max`, `t5_punctuation_chars`).

**Important gap, verified against the code and confirmed by testing:** the EARS check, the
indefinite-article check, and the zero-`shall` check are gated by a literal Python string
comparison -- `if profile == "spec":` and `if profile in ("spec", "design"):` in
`src/ste100/checks_atomicity.py` -- **not** by whether `"ears"` appears in that profile's `tests`
list in the config. `the default preset` deliberately keeps its formal-requirements profile
named `spec` specifically so this keeps working out of the box; renaming it would silently
disable EARS/zero-shall/indefinite-article checking with no error. Verified: a well-formed EARS
sentence under the `spec` profile produces no EARS finding, only its unrelated T1 hit:

```
"The system shall log every request." (profile: spec)
$ ste_lint.py --config the default preset requirements/core.md
requirements/core.md:3:28 ERROR T1 STE-T1-SUB-0383 -- Replaceable: 'request' -> 'ask'.
```
(no STE-T5-EARS-0001 -- the sentence conforms to the Ubiquitous EARS template)

**Severity:** `error` for multi-shall/and-or/oblique-slash; `warning` for punctuation density;
`review` for zero-shall and (outside `spec`) EARS; all capped to `review` under `prose`.

**Verified before/after:**

```
Before: "The renderer shall draw the frame and the audio mixer shall play the cue."
$ ste_lint.py --config the default preset --profile spec t5_before.md
t5_before.md:3:1 ERROR T5 STE-T5-MULTI-0001 -- Non-atomic: 2 'shall' imperatives in one sentence.

After:  "The renderer shall draw the frame.\n\nThe audio mixer shall play the cue."
-> 0 findings
```

## T6 -- Zero-information

**What it detects:** words and phrases that occupy space in a sentence without adding checkable
content: fillers/intensifiers ("very," "just"), overused vocabulary, weasel words ("many players
reported"), corporate speak ("circle back"), AI-writing tells (hedging openers like "It is
important to note that," conclusion markers, and high-confidence machine artifacts like a
leaked citation token), and nominalizations (a weak verb + noun where one verb would do --
"perform an evaluation" instead of "evaluate").

**Why it matters:** this is the test most directly about signal-to-noise. Every one of these
patterns reads as if it's saying something while adding zero falsifiable content -- the
opposite of the STE goal of one clear meaning per sentence.

**Data:** `src/ste100/data/filler.json` (fillers/intensifiers, overused vocabulary, weasel words,
corporate speak, nominalization weak-verb/suffix lists) and `src/ste100/data/ai_tells.json` (phrases,
machine-artifact regexes).

**Severity:** `error` in every profile -- T6 is the third of the three tests the `prose`
fallback keeps at `error`.

**Verified before/after (one sentence hits three different T6 sub-rules plus a T1 hit):**

```
Before: "It is important to note that the build is very stable."
$ ste_lint.py --config the default preset --profile prose t6_before.md
t6_before.md:3:1  ERROR T1 STE-T1-SUB-0328 -- Replaceable: 'It is' -> ''.
t6_before.md:3:1  ERROR T6 STE-T6-AI-0004 -- Zero-information (AI tell, hedging_opener): 'It is important to note that'.
t6_before.md:3:43 ERROR T1 STE-T1-SUB-0416 -- Replaceable: 'very' -> ''.
t6_before.md:3:43 ERROR T6 STE-T6-FILL-0346 -- Zero-information (filler/intensifier): 'very'.
t6_before.md:3:43 ERROR T6 STE-T6-WEASEL-0018 -- Zero-information (weasel word): 'very'.

After:  "The build is stable."
-> 0 findings
```

Nominalization example, from `tests/corpus_dirty/dirty_t6.md`:

```
dirty_t6.md:10:15 ERROR T6 STE-T6-NOM-0001 -- Zero-information (nominalization): 'perform an evaluation' -- prefer a single verb.
```

## Structural (`S7`) checks

**What they detect:** seven mechanical checks run alongside T5 on every sentence unit: a bare
number with no unit and no `%` (`S7-BARENUM`); an indefinite article `a`/`an` in a single-`shall`
`spec` sentence, where `the` is preferred (INCOSE R5, `S7-ARTICLE`); passive voice
(`S7-PASSIVE`); the literal word `tbd` (NASA SEH: use `TBR` with a best estimate instead,
`S7-TBD`); an abbreviation not in the allowlist and not declared `ACRONYM` in a
`terminology.csv` registry (`S7-ABBR`); a deprecated or premature technical term from that same
registry (`S7-TERM`); and the word `must` where `shall` is meant to be the one mandatory keyword
(`S7-MUST`).

**Why it matters:** these are the checks that make prose read like engineering writing instead
of marketing copy -- concrete units, one mandatory keyword, no jargon introduced before it's
defined.

**Important note on how `structural` is wired:** unlike T1-T6, there is no separate dispatch
for `"structural"` in `ste_lint.py`'s per-unit loop -- it only checks for `"T1"`, `"T3"`,
`"T6"`, `"budgets"`, `"T2"`, `"T4"`, `"T5"` membership in a profile's `tests` list. All seven
structural checks live inside `check_t5_and_structural()` and fire automatically whenever
`"T5"` is in a profile's `tests`. Listing `"structural"` (or `"S7"`) in a profile's `tests` in
the config is decorative -- accurate as a label, but not something the code consults.

**Data:** the checks themselves are in `src/ste100/checks_atomicity.py`; the abbreviation allowlist
and unit vocabulary are config-driven (`abbreviation_allowlist`, `s7_units`); the
deprecated/premature-term data comes from a project's own `terminology.csv`, if it has one (see
`src/ste100/engine.py:index_terminology()` -- this stays a harmless no-op with zero findings from
`S7-TERM` until a project actually maintains that registry; ships header-only by default, and
that is expected, not a bug).

**Severity:** `warning` for bare-number/passive/abbreviation, `review` for indefinite-article,
`error` for tbd/deprecated/undefined-term, `warning` for must (except `error` in `spec`); all
capped to `review` under `prose`.

**Verified before/after:**

```
Before: "Load time is 50 right now."
$ ste_lint.py --config the default preset --profile reference --stats structural_before.md
structural_before.md:3:14 WARNING structural STE-S7-BARENUM-0001 -- Structural: bare number '50' with no unit and no %.

After:  "Load time is 50ms."
-> 0 findings
```

## CSV integrity (`csv`, `STE-CSV-0001`..`STE-CSV-0010`)

**What it detects:** cross-file referential integrity for a specific document-control registry
schema -- four CSV kinds recognized *by exact filename* (`truths.csv`, `timeline.csv`,
`terminology.csv`, `decisions*.csv`): superseded/supersedes resolution and cycle detection,
`linked_truth_ids` / `source_decision_id` foreign-key resolution, duplicate-ID detection across
decision files, required and staleness-checked `review_by` dates, and enum validation of
`status` columns.

**This is Veistra's own private schema, not a generic CSV feature.** `the default preset`'s
`csv` profile deliberately does not list `"csv_integrity"` in its `tests`. **That said, verify
before you rely on it:** `check_csv_integrity()` is called unconditionally in `ste_lint.py`'s
`main()` for every discovered `.csv` file, regardless of any profile's `tests` list -- so
omitting `"csv_integrity"` from `tests` is currently cosmetic, not a real gate. See
`docs/configuration.md` for how much a generic CSV
without these exact filenames is actually exposed (very little: `kind_of()` returns `None` for
any CSV that isn't named exactly `truths.csv`/`timeline.csv`/`terminology.csv`/`decisions*.csv`,
which gates most of these checks off; the one check that isn't kind-gated is the `review_by`
staleness check, so a generic CSV with a `review_by` date column in the past could still
produce a spurious `STE-CSV-0008` finding).

**Data/logic:** `src/ste100/csv_integrity.py`.

**Severity:** hardcoded per-finding in `csv_integrity.py` (`"error"` for all structural
integrity findings, `"warning"` for stale-but-not-overdue `review_by`) -- this family does not
go through `Engine.severity()` at all, so `severity_overrides` cannot change its tier.

**Verified before/after** (run with `the veistra preset`, since this is the schema it targets):

```
Before (decisions.csv row): status=SUPERSEDED, superseded_by empty
$ ste_lint.py --config the veistra preset --profile csv decisions-before.csv
decisions-before.csv:0:1 [DEC-001:superseded_by] ERROR csv_integrity STE-CSV-0001 -- CSV integrity: status=SUPERSEDED needs a resolving superseded_by.

After: add a DEC-002 row with status=ACTIVE and supersedes=DEC-001, and set
       DEC-001's superseded_by=DEC-002
-> 0 findings
```

```
$ ste_lint.py --config the veistra preset --explain STE-CSV-0006
STE-CSV-0006: CSV integrity: no duplicate IDs within a file or across decision files.
```

## Budgets (`STE-BUD-0001`..`STE-BUD-0005`)

**What they detect:** four size limits: a sentence over its profile's word budget
(`BUD-0001`), a paragraph over 6 sentences (`BUD-0002`), a CSV field over its word budget
(`BUD-0003`, Veistra-registry-specific target names, see below), and a whole file over its word
budget (`BUD-0004`, likewise Veistra-specific target paths). A fifth, `BUD-0005`
(`truths.csv` over 40 rows), is emitted directly from `csv_integrity.py`, not from the budgets
engine.

**Data:** `src/ste100/data/budgets.json` -- `sentence_budgets` (keyed by **profile name**),
`csv_field_budgets` and `whole_file_budgets` (keyed by **literal Veistra filenames** like
`truths.csv:statement` and `core/00-READ-FIRST.md`), and `paragraph_budget`.

**A consequence of renaming profiles, verified as harmless:** `sentence_budgets` is keyed by
profile name (`core`, `spec`, `design`, `prose`, `vision`). `the default preset`'s `reference`
profile has no matching entry, so `Engine.sentence_budget_by_profile.get(profile, ...get("prose"))`
falls back to the `prose` entry (30 words, `warning`) -- it does not crash, and `spec` keeps its
own dedicated 25-word/`error` budget since that profile name is unchanged. `csv_field_budgets`
and `whole_file_budgets` simply never match anything in a generic project (no `truths.csv`, no
`core/00-READ-FIRST.md`) and stay silent no-ops, same as the CSV-integrity family above. This
`src/ste100/data/budgets.json` file is out of this preset's scope to change.

**Verified example:**

```
$ ste_lint.py --config the default preset --profile prose tests/corpus_dirty/dirty_paragraph.md
dirty_paragraph.md:4:1 WARNING budget STE-BUD-0002 -- Budget: paragraph has 7 sentences, over the 6-sentence budget.
```

## Standards cited in this codebase

- **ASD-STE100** -- the overall discipline this tool is built around (controlled vocabulary,
  short unambiguous sentences).
- **INCOSE** guides to writing requirements -- R5 (definite article), R7 (measurable/testable
  language, T2), R8 (no escape clauses, T3), R9 (no open-ended clauses, T3), R10 (no
  superfluous infinitives, T3), R19 (limit combinators per sentence, T5), R24 (pronoun
  antecedents, T4).
- **NASA Systems Engineering Handbook (SEH)** -- `and/or` prohibition (T5), `TBD` vs `TBR`
  guidance (structural), punctuation-density guidance (T5).
- **MIL-STD-961E** -- `and/or` prohibition (T5).
- **EARS** (Easy Approach to Requirements Syntax) -- the five sentence templates checked in
  `spec`-named profiles (T5).
- **Femmer et al.**, empirical requirements-smell research -- comparative/superlative baseline
  checks (T4).
- **QuARS** -- unfalsifiable/vague term detection (T2) and optionality (T3).

The lexical data has separate, third-party provenance; see the next section.

## Data provenance

Parts of the word and phrase tables in `src/ste100/data/` are derived from third-party
open-source projects. Each shipped file carries its own provenance: `substitutions.json`
in a per-entry `source` field, and `hedges.json`, `filler.json`, `vague.json` and
`ai_tells.json` in a table-level `sources` header.

`NOTICE` names each upstream and its copyright holder. `THIRD-PARTY-LICENSES.md`
reproduces the full license text of each, which those licenses make mandatory for a
